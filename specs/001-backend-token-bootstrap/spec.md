# Spec 001：后端安装自动生成并展示 Token

状态：已实现，验证结果与待验收项见 `tasks.md`

## 1. 需求

用户执行后端安装后，安装流程自动生成登录 Token、持久化配置并输出给用户。不再要求用户单独执行随机数命令、复制示例 JSON、替换占位值或手工设置 Token 文件权限。

交付包括规格、后端初始化命令、Linux/Docker 安装脚本、验证与部署文档。

## 2. 当前代码基线

审查提交：`eca7155290ed330f457cd9d20df15ca34514a6fc`。

- `cmd/server/main.go`：普通服务要求配置 `PIH_TOKENS_FILE`、`PIH_TOKENS`、`PIH_TOKEN` 中恰好一种；缺失或冲突即报错。旧单 Token 的空间固定为 `default`。
- `configuredAdminSpace`：单空间可自动确定管理员；多空间可显式指定，或使用已有 `admin` 空间。
- `internal/backend/server.go`：启动会同步配置中的用户，因此误生成新的 Token 映射可能改变既有账号状态，不能仅凭配置文件不存在判定为新安装。
- `README.md`、`docs/linux-amd64.md`：要求手工准备 Token 文件；Linux 当前只发布可执行文件，没有系统服务安装器。
- `docs/docker.md`：要求执行 `openssl rand` 或修改示例文件。`compose.yaml` 的 `/config` 挂载只读；容器以 UID/GID `10001:10001` 运行，不能直接在运行中的 `/config` 生成配置。
- 飞牛模式设置 `PIH_FNOS_SOCKET` 后允许不配置静态 Token，网页登录走平台身份链路。它不需要新增初始管理员 Token。

## 3. 范围与建议

建议覆盖普通 Linux 后端和 Docker Compose 安装。保持现有 Token 鉴权、管理员与空间归属模型。

推荐新增统一的后端初始化能力，由安装入口自动调用：用户只执行安装，初始化是内部步骤。生成逻辑放在 Go 中，避免多个脚本分别处理随机数、JSON、权限和已有数据判断。

正常服务启动继续校验配置，不在每次缺少配置时自行创建管理员。这样能够区分新安装与运行时配置错误。

实现补充：没有显式来源时，普通服务读取数据目录中安装器已生成的 `tokens.json`；文件不存在仍报错。此回退不适用于飞牛模式。

不涉及 Mac 客户端、飞牛 SSO、Android 管理壳、Token 轮换、账号恢复、公开注册、TLS 自动配置或自动更新。现有手工配置继续作为高级部署方式。

## 4. 确定的行为

| 安装时状态 | 预期行为 |
| --- | --- |
| 无显式 Token 来源、无已保存凭证、全新数据目录 | 自动生成初始管理员 Token，保存配置，启动并展示结果 |
| 已有合法配置，重复安装或升级 | 复用 Token、管理员空间和数据，不重新生成 |
| 用户提供一种合法 Token 来源 | 使用该配置，不另建默认管理员、不改变空间 ID |
| 同时提供多种 Token 来源 | 明确报错，不写入任何新凭证 |
| 显式提供的文件不存在、损坏或不可读 | 明确报错，不自动覆盖或切换来源 |
| 数据目录已有数据库、媒体或其他实例数据，但凭证缺失 | 停止初始化，说明需要恢复原配置；不生成新身份 |
| 自动管理的凭证文件损坏或权限不符合要求 | 停止并说明文件问题，不用新 Token 替换 |
| 随机数、权限设置或持久化失败 | 安装失败，不启动服务，不输出可用 Token 或成功提示 |
| 凭证已写入，但后续启动失败 | 保留凭证供重试；明确报告未启动成功 |
| 两个安装进程同时初始化 | 串行处理；最多创建一份配置，另一方复用或明确报冲突 |
| 飞牛免 Token 模式 | 继续现有流程，不自动创建静态管理员凭证 |

“全新数据目录”应采取保守定义：不存在，或为空。只允许初始化程序自身可识别的控制文件；出现不认识的已有文件时说明原因并停止，不能推测其可丢弃。

## 5. 凭证与持久化

- 使用 `crypto/rand` 生成 32 字节随机值，编码为 64 个十六进制字符。
- 全新默认空间为 `admin`；若安装者指定合法管理员空间 ID，则使用该 ID。既有实例沿用原 ID，尤其不能把旧 `default` 改为 `admin`。
- 自动生成的 JSON 使用现有空间到 Token 的映射格式，不引入第二套认证协议。
- 文件权限为 `0600`，由实际读取它的服务用户拥有；父目录限制访问。Docker 初始化与主服务使用相同 UID/GID。
- 创建过程具备互斥、完整写入、持久化及不覆盖已有目标的保证。不能先创建宽权限明文文件再收紧权限。
- 配置只在持久化成功后用于启动和展示。异常中断后再次执行应能复用完整文件，或报告不完整状态，不自动轮换。
- 安装配置和服务启动必须使用同一解析后的路径。凭证路径应纳入备份说明。

## 6. 安装结果展示

安装入口在服务健康检查成功后直接向执行安装的用户输出：访问地址、管理员空间、登录 Token、凭证保存位置。

示意（占位符不可作为真实凭证）：

```text
PocketIMG 安装完成
访问地址：http://<部署主机>:8080
管理员空间：admin
登录 Token：<本次实例的 Token>
凭证已保存：<实际路径>
```

- 地址来自实际部署配置；未配置域名或主机地址时明确标注主机占位，不能把 `0.0.0.0` 当作用户访问地址。
- Linux 使用回环监听时说明该地址只可在服务器本机访问；不为展示地址自动改变监听或 Cookie 策略。
- 首次安装无需用户另执行查看日志、读取文件或生成 Token 的命令。
- 普通服务启动、重启、健康检查和日常日志不打印 Token；安装器的面向用户输出允许包含 Token，这是本需求的明确行为。
- 重复执行面向用户的安装入口可重新展示复用的管理员 Token；无人值守升级不主动输出凭证。
- 非交互安装也把结果返回调用者，不因没有终端而静默丢失凭证；不把明文嵌入命令参数或 HTTP URL。
- 如启动失败，保留已保存配置，输出失败原因及配置位置，不显示“安装完成”。

## 7. 验收条件

1. 空目录执行一次安装，自动获得可登录管理员页面的 Token；无需手工准备凭证。
2. 输出 Token 与落盘配置一致，文件权限、所有者和服务可读性正确。
3. 重复安装、服务重启和升级后原 Token 有效，空间 ID 和已有图片归属不变。
4. 有效自定义文件、内联 JSON、旧单 Token 的原有行为均保留；多来源冲突仍失败。
5. 配置缺失但存在实例数据时，不生成新配置、不修改数据库或媒体文件。
6. 损坏配置、权限不足、随机数失败、写入失败及并发初始化都不产生被误报为成功的新身份。
7. Docker 在只读根文件系统和固定非 root UID 下完成初始化与正常运行；重建容器仍可使用原 Token。
8. 首次安装结果可直接看到 Token，日常服务日志没有 Token。
9. 飞牛无静态 Token 启动及现有登录链路不受影响。

## 8. 分析结论

需求可行，主要工作是补齐安装入口、初始化持久化和结果展示。单独在文档里增加一条随机数命令不满足需求；安装脚本内部调用初始化命令则满足，因为用户不需要感知或执行这个独立步骤。
