# Implementation Plan 001

状态：已实现，系统级验证范围见 `tasks.md`。以 `spec.md` 的行为和验收条件为准。

## Phase 1：统一初始化能力

1. 在现有后端可执行文件中增加内部安装使用的 `init` 子命令，在服务启动前分派；不启动 HTTP、不执行数据库用户同步。
2. 提取并复用 Token 来源、JSON、空间 ID 和管理员选择校验；保持正常启动时的缺失配置错误。
3. 初始化先解析显式配置和已有自动配置，再判定是否全新安装。检查不应通过启动数据库或迁移来完成，以免诊断本身修改旧数据。
4. 用 `crypto/rand` 生成初始凭证；实现安装互斥、受限权限、完整持久化和不覆盖提交。具体文件提交机制需在 Linux 上验证并发和崩溃边界。
5. 向安装器返回可直接展示的结果文本：管理员空间、Token、配置位置。脚本捕获文本，健康检查后整体展示，无需额外 JSON 解析依赖。该输出不接入服务日志。

## Phase 2：Linux 安装入口

1. 新增安装脚本，第一版面向已取得并校验的 Linux 发布二进制，完成服务账号、目录、二进制和 systemd 配置。自动下载与版本发现不纳入本次需求。
2. 使用 `/etc/pocketimg/credentials/tokens.json`、`/var/lib/pocketimg` 和 `/usr/local/bin/pocketimg`。凭证子目录允许服务身份初始化；父目录由 root 管理，保护 `service.env` 不被服务改写。
3. 以服务身份执行初始化；安装脚本内部接收结果，不要求用户另执行 `init`。
4. 复用既有部署配置；发现无法识别的现有 unit 或路径冲突时明确失败，不覆盖用户配置。
5. 启动服务并检查健康状态，成功后展示安装结果；失败保留凭证并报告故障。
6. 保留手动运行二进制的高级方式，主安装说明不再以手工生成 Token 为前置条件。

## Phase 3：Docker Compose 安装入口

1. 新增 Compose 安装包装脚本，以相同镜像和 UID 运行一次性初始化，再启动常驻服务。
2. 自动生成的凭证置于持久化数据卷 `/data/tokens.json`。普通服务在没有显式来源时读取这个已存在文件，不自动生成；不需要持久化额外 Compose 环境变量，也不写入只读 `/config`。
3. 显式提供 `/config` 文件或旧环境 Token 时继续沿用；不同时配置自动文件和环境 Token。初始化与启动必须使用同一 Compose 项目、数据卷及配置。
4. 主服务启用前完成一次性初始化；包装脚本接收输出并在健康检查通过后展示，无需用户查容器日志。
5. 保留直接使用 Compose 的高级入口；文档说明自动化体验来自包装脚本，不能宣称裸 `docker compose up -d` 会向终端展示 Token。

## Phase 4：验证和文档

1. 使用临时目录验证行为矩阵，包括已有数据保护、并发和中断后重试。
2. 使用隔离 Linux/systemd 环境及临时 Docker 卷验收实际安装、登录、重启与复用，避免操作开发者已有服务或数据。
3. 回归现有配置解析和飞牛免静态 Token 启动。
4. 更新 README、Linux 和 Docker 部署说明：主路径为一次安装，包含结果示例与备份路径；手工 Token 配置移至高级配置。
5. 代码与对应运行验证完成后再勾选任务。无法运行的系统级验证应明确标为未验证。
